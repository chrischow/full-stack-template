# Plan: Pulumi SSM parameters project

## Context

Create `infra/secrets` as a standalone Pulumi project that manages AWS Systems Manager Parameter Store values **and a dedicated KMS key solely for encrypting its `SecureString` parameters**. Start with a `prototype` stack; design the naming and configuration so `staging` and `production` stacks can be added later. The source is the repo-root `.env.development`, which contains 30 variable names. Import **all** entries, not just the backend-required subset. Store `DB_PASSWORD`, `SESSION_SECRET`, `OAUTH_CLIENT_SECRET`, `OTP_SECRET`, and `AWS_SECRET_ACCESS_KEY` as SSM `SecureString`; store every other entry as SSM `String`.

The repo-root `.env.development` is tracked and is for development only; do not change it as part of this work. Neither the new Pulumi project nor this plan should reproduce any values. Pulumi config secrets are encrypted in `Pulumi.prototype.yaml` by the stack's **external** secrets-provider key. The separate, project-managed SSM key encrypts the five `SecureString` values; SSM `String` values remain readable to anyone authorized to read those parameters. Protecting Pulumi state, SSM values, and access to the development file are separate considerations.

## Approach

- Follow the existing pnpm/TypeScript Pulumi project pattern and use `@pulumi/aws` for SSM parameters. Do not put application secrets in `infra/bootstrap` or create runtime SSM consumers as part of this project.
- Define each parameter name as `/${pulumi.getStack()}/${originalEnvName}`, preserving the original name exactly (e.g. `/staging/OTP_SECRET`). Read all 30 values from encrypted Pulumi stack config via `config.requireSecret(originalEnvName)`, using `secrets:<originalEnvName>` keys. When staging and production are added, each gets its own independent stack config and namespaced parameters.
- Configure **all 30** entries as Pulumi secret config (even those destined for SSM `String`), following the user's `pulumi config set ... --secret` intent. Stack YAML contains encrypted ciphertext, not plaintext, once a KMS-backed Pulumi secrets provider is set up. Protect values from CLI argument/history/process-list leaks: omitting `<value>` and using the interactive CLI prompt, or a safe no-logging import helper if automatic population is desired. Do not print values or use `--show-secrets` for verification.
- Use a fixed five-name `SecureString` classification; all remaining names become `String`. Create one customer-managed, symmetric SSM KMS key per stack and pass its ARN as `keyId` on **only** the five `SecureString` parameters. Set rotation and a deliberate key policy; protect against accidental key deletion. Do not use the new key as the Pulumi secrets provider: the external Pulumi key must be usable before this program runs. Validate the configured AWS account against the caller identity before writing, following the bootstrap project's safety pattern. Use the provider's configured `aws:region` independently of the application `secrets:AWS_REGION`; do not add a stack-name allowlist.
- Document distinct access boundaries: the secrets deployer needs Pulumi-provider decrypt, SSM write/refresh and SSM-key management/use; the runtime identity needs scoped SSM reads and `kms:Decrypt` on the **SSM** key for `SecureString` reads, but no Pulumi-provider key access. Plan key-policy administration/recovery and scope SSM-key usage to appropriate parameter ARNs/encryption context where feasible. Disabling/deleting the SSM key would make encrypted values unavailable.
- The **user**, not the implementation assistant, will populate the 30 encrypted config keys manually from `.env.development` using `pulumi config set <key> --secret` and the interactive prompt, after creating/selecting the KMS-backed `prototype` stack. Provide step-by-step instructions; do not initialize or configure the stack on the user's behalf. Do not put `<value>` in command-line arguments: literal `pulumi config set <key> <value> --secret` can disclose it through shell history and process listings. The Pulumi program reads stack config, not `.env.development` at deployment time; do not add an import utility.
- Preserve the repo-root source file's existing key set: `NODE_ENV`, `APP_PORT`, `APP_DOMAIN`, `APP_NAME`, `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USERNAME`, `DB_PASSWORD`, `KV_TTL_SECONDS`, `SESSION_NAME`, `SESSION_SECRET`, `SESSION_COOKIE_MAX_AGE`, `OAUTH_BASE_URL`, `OAUTH_CLIENT_ID`, `OAUTH_CLIENT_SECRET`, `OAUTH_CLIENT_CALLBACK_URL`, `OTP_REQUEST_TIMEOUT_SECONDS`, `OTP_VALIDITY_SECONDS`, `OTP_MAX_RETRIES`, `OTP_SECRET`, `AWS_REGION`, `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_SES_ENDPOINT`, `PASSKEY_RP_ID`, `PASSKEY_ORIGIN`, `PASSKEY_REGISTER_TIMEOUT_SECONDS`, `PASSKEY_AUTHN_TIMEOUT_SECONDS`, `PASSKEY_VERIFICATION_DAYS`. Treat this as an exact key inventory for the initial project, and avoid confusing the `secrets:AWS_REGION` app parameter with the `aws:region` provider setting. Resolve before implementation details are finalized.
