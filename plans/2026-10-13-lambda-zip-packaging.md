# Plan: package the NestJS API and React SPA for AWS Lambda ZIP

## Context

- `apps/backend/src/app.module.ts` serves `apps/frontend/dist` from a path relative to the compiled backend. Keep the API and SPA together in the ZIP at the expected relative paths.
- The backend currently parses required environment configuration during import and `apps/backend/src/main.ts` starts a listening server. A separate effort will change the backend to fetch secrets from SSM at runtime. This work renames the app's explicit SES credential variables from Lambda-reserved `AWS_ACCESS_KEY_ID` and `AWS_SECRET_ACCESS_KEY` to `SES_ACCESS_KEY_ID` and `SES_SECRET_ACCESS_KEY`; it does not implement credential sourcing or runtime configuration. The current application cannot start without its required configuration.
- Produce a self-contained ZIP targeting Linux `x86_64` on managed `nodejs22.x`, with a root launcher for Lambda Web Adapter (LWA). No configuration bootstrap, SSM fetch, KMS decrypt, or `process.env` mutation belongs in this packaging effort. Do not create an execution role, change `infra/secrets`, provision a function, or upload/deploy the ZIP.
- LWA setup is in scope, but configuring the Lambda function's environment and providing backend runtime configuration are not. The deployment must attach a pinned, `x86_64`-appropriate LWA layer, set handler `run.sh`, set `AWS_LAMBDA_EXEC_WRAPPER=/opt/bootstrap`, and align LWA's port with the app. With `APP_PORT` absent, the unchanged backend listens on port 3000, so deployment must set `AWS_LWA_PORT=3000` unless the separate runtime-configuration effort supplies matching ports. These LWA settings are deployment prerequisites, not values injected by the ZIP. The current backend still requires configuration at import time, so this package alone is not deployment-ready.

## Approach

1. Use the existing workspace builds and compile the Nest backend before bundling emitted JavaScript with ESBuild (`esbuild`), retaining TypeScript decorator metadata. Bundle for Node.js 22 in CommonJS format and explicitly account for workspace dependencies, generated Prisma client, native modules, and dynamically loaded assets.
2. Stage the compiled backend under `apps/backend/dist/` and the frontend under `apps/frontend/dist/` so the existing static-file path resolves. Include all runtime dependencies and assets required for a clean, self-contained Linux `x86_64` ZIP; exclude development dotenv files and unrelated workspace/build artifacts.
3. Rename the app-facing SES credential keys to `SES_ACCESS_KEY_ID` and `SES_SECRET_ACCESS_KEY` in the env schema, mail service, and development env file. Keep explicit SES credentials and existing required validation; leave the existing SSM/Pulumi `AWS_*` names unchanged. The separate runtime-SSM effort must map those existing parameter names to the new app-facing keys.
4. Add executable root `run.sh` to start the bundled Nest server with Node, without reading SSM, decrypting KMS values, or setting application environment variables. Use LWA's managed-runtime ZIP integration: deployment attaches the LWA layer and configures its execution wrapper and handler. Document the required wrapper, port alignment, and architecture; do not provision the function or inject its environment in this effort. Keep backend credential sourcing and runtime-configuration work in the separate effort.

## Files to modify

- `apps/backend/src/env/schema.ts`, `apps/backend/src/mail/mail.service.ts`, and root `.env.development`: use app-facing `SES_ACCESS_KEY_ID` and `SES_SECRET_ACCESS_KEY` instead of the reserved `AWS_*` names, without changing how credentials are sourced.
- Root-level `run.sh` (new): executable launcher that starts the backend bundle under LWA without loading or setting configuration.
- Root-level packaging script (new; e.g. `scripts/bundle-lambda.sh`): build, bundle, stage, and archive the backend, launcher, and SPA; inspect the output for missing files and broken workspace links.
- Root `package.json` and `pnpm-lock.yaml`: add a `bundle` script and ESBuild (`esbuild`) as an explicit build-time dependency.
- An appropriate README: document artifact layout, target platform, build process, LWA layer/handler/wrapper/port setup, and remaining runtime-configuration and deployment prerequisites.
- Do not edit `apps/backend/src/main.ts`, its generated `main.js`, `infra/secrets`, or the Pulumi deployment projects. Backend configuration and mail-service edits are limited to the SES credential rename above; existing SSM parameter names and types remain unchanged.

## Reuse

- Existing `nest build`, workspace package builds (including Prisma generation and API-contract exports), and frontend `tsc -b && vite build`.
- Existing `ServeStaticModule` relative layout, API exclusions, and frontend same-origin `/api/v1` client.
- Existing container build as a reference for staging production dependencies and frontend assets, without assuming its container filesystem or installed modules are present in the ZIP.
